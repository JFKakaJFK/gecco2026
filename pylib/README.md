# Python bindings

The Python bindings are mostly autogenerated using [litgen](https://github.com/pthom/litgen) and [nanobind](https://github.com/wjakob/nanobind). This means the C++ code directly is the Python interface. This is both good and bad: there is no extra boilerplate code to write, but the C++ code also is subject to limitations.

Under the hood, first all headers are amalgamated to `pylib/include/amalgamation.h`, then litgen parses this header file and generates Python stubs (`pylib/pygom/__init__.pyi`) and the nanobind binding code. The binding code is then compiled and linked with the original code during `pip install`. Beyond that, there are some options in `scripts/autogenerate_bindings.py`, e.g. what to exclude and how to rename C++ to Python types. Since the parser used by litgen is not the compiler (!), there are several limitations on the C++ code and things to note:

- As long as the [corresponding header](https://nanobind.readthedocs.io/en/latest/exchanging.html) is included in `pylib/nanobind/bindings.cpp`, the conversion between Python and C++ objects and types is mostly seamless - e.g. subclasses are casted to base classes or a numpy `ndarray`s are zero copy `Eigen::Ref<...>`s as long as the underlying data is a match.
- Python has no references, so input/output parameters do not work for Python scalars - e.g. calling the the C++ function `void modifyX(double& x)` from Python does not change the passed value (https://pthom.github.io/litgen/litgen_book/05_05_00_functions.html?highlight=box#handle-modifiable-immutable-params).
- C++ template metaprogramming support is limited. litgen only supports supplying a single template argument (via the options in `scripts/autogenerate_bindings.py`), and it can be the case that the binding code generated is insufficiently specialized, causing the compilation to fail without patching the bindings first (e.g. `SoASet::add` -> `SoASet<Eigen::ColMajor>::add`).
- The parser is not the compiler and only supports up to C++14 (syntax, semantics like newer standard library headers tend to work just fine). However, the parser mostly fails silently and litgen only needs the signatures - so only those need to be parsed correctly. Another consequence of this is that it can happen that the bindings generate without error, but compiling the bindings fails. Tip: sometimes re-ordering code can make the difference between correct bindings or compilation errors during `pip install` (in particular when litgen generates invalid default constructors, even when explicitly deleted).
- The C++ root namespace becomes the Python module root, and nested namespaces become nested modules. I have not tried re-adding the `lib/bench/methods` namespaces as per the folder structure after adding the amalgamaion step, but before there were issues where the submodule was re-declared per input header.
- Parsing happens per litgen input file, so without the amalgamation step class inheritance that is split up across headers is not properly registered (https://github.com/pthom/litgen/issues/5)


Tip: if srcML parsing fails, disable the amalgamation step and bisect where the error is coming from by commenting out half of the previously amalgamated header (e.g. starting from your last edit) repeatedly - until the srcML error disappears when trying to generate the remaining bindings. The srcML errors are rarely useful (after all, the parser has been thrown off) and it can seem arbitrary what works or not (e.g. C++20 `std::span` is fine but not C++14 generic lambdas).

Also, once the bindings are in place and the python module has been installed (e.g. via `pip install -e .`), generating the bindings builds the previous version - sometimes that fails, and to get around it the module has to be uninstalled (e.g. `uv pip uninstall -v .`) or the autogenerated parts of `nanobind/bindings.cpp` have to be deleted to make the build succeed.
